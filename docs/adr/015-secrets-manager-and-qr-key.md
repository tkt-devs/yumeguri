# ADR-015: シークレットは Secrets Manager に置き、QR の署名の鍵もそこに置く

- 状態：決定
- 日付：2026-10-30

## 背景

DB のパスワード・Google のクライアントシークレット・QR のトークンの署名の鍵などの置き場所を決める。QR のトークンは、署名つきのトークン（店 ID・nonce・期限・鍵 ID）にする（要件定義書 FR-STP-01）。

## 選択肢

| 選択肢 | 良いところ | 悪いところ |
| --- | --- | --- |
| Secrets Manager | ECS のタスク定義から直接読み込める。自動のローテーションの仕組みがある | 1つにつき月 0.40ドル |
| Systems Manager Parameter Store（SecureString） | 標準のものは無料 | ローテーションの仕組みがない |
| AWS KMS で署名する（鍵を AWS の外に出さない） | 鍵そのものを、アプリが一度も持たない | 署名のたびに KMS を呼ぶので遅く、呼んだ回数だけ費用がかかる |

## 決めたこと

- シークレットは **Secrets Manager** に置く。ECS のタスク定義の `secrets` で、起動時に環境変数として渡す
- QR のトークンは、**HMAC-SHA256 で署名**する。鍵は Secrets Manager に置き、**鍵 ID（`kid`）** を付ける
- API は、起動時に鍵を読み、一定の時間ごとに読み直す。鍵を入れ替えるときは、しばらく古い鍵と新しい鍵の両方で検証する（トークンの期限が60秒なので、数分で足りる）

## 理由

- シークレットの数が少ないので、費用は月に数ドルで済む
- 鍵 ID を付けておけば、鍵を入れ替えている間も、QR が使えなくならない
- HMAC は速いので、30秒ごとの QR の発行と、チェックインのたびの検証に向いている

## 捨てた選択肢

- **Parameter Store**：ローテーションの仕組みがなく、Secrets Manager の学習（Day 79）にならないので採らない
- **KMS で署名する**：QR の発行と検証のたびに KMS を呼ぶのは、遅さと費用に見合わないので採らない

## リスクと、その対策

- 鍵を API のメモリに持つので、API のタスクが乗っ取られると鍵も漏れる。鍵を入れ替える手順を Runbook に書いておく
- シークレットの値を、ログ・エラー・コミットに出さない（`AGENTS.md`）
