# ADR-004: ログインの状態を、セッションの Cookie で持つ

- 状態：決定
- 日付：2026-10-30

## 背景

Google でログインしたあと、「誰がログインしているか」をどこに持つかを決める。ブラウザの JavaScript で読み書きできる場所（`localStorage`）に、トークンを置く方法もよく使われる。

## 選択肢

| 選択肢 | 良いところ | 悪いところ |
| --- | --- | --- |
| サーバーにセッションを置き、Cookie にはランダムな値だけを入れる | JavaScript から Cookie を読めない（`HttpOnly`）。サーバー側で、いつでも無効にできる（ログアウト・利用の停止） | リクエストのたびに、DB でセッションを探す必要がある |
| JWT を `localStorage` に置く | サーバーで何も探さなくてよい | 画面に悪いスクリプトが入り込む攻撃（XSS）で、トークンを盗まれる。期限までは無効にできない |
| JWT を Cookie に置く | XSS で直接は読まれない | 期限までは無効にできない。ログアウト・利用の停止をすぐに効かせられない |

## 決めたこと

**サーバー側のセッション** にする。

- Cookie（`sid`）には、ランダムな長い値だけを入れる。DB の `Session` の表には、その値の **SHA-256（`token_hash`）** だけを保存する
- セッションの期限は最長30日。ログアウトしたら `revoked_at` を入れる
- ログインの前後で、セッションを作り直す（ログインの前の Cookie を使い続けさせない）

## 理由

- XSS があっても、Cookie の値を JavaScript で盗まれない
- ログアウト・すべての端末からのログアウト・利用の停止を、すぐに効かせられる
- DB には値のハッシュしか置かないので、DB の中身が漏れても、そのままセッションを乗っ取られない

## 捨てた選択肢

- **JWT を `localStorage` に置く**：XSS でトークンを盗まれるので採らない
- **JWT を Cookie に置く**：すぐに無効にできないので採らない

## リスクと、その対策

- リクエストのたびに DB を読むので、少し遅くなる。遅さが問題になったら、ElastiCache にセッションを短く保存することを考える
- 期限切れのセッションの行がたまる。定期的に消す処理を作る（v0.2 の定期処理）
