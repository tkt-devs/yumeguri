# ADR-002: API とワーカーを ECS（Fargate・ARM）で動かす

- 状態：決定
- 日付：2026-10-30

## 背景

API（Hono）とワーカー（Python）を、コンテナとして AWS で動かす。ワーカーは、SQS からジョブを待ち続ける、長く動く処理である。CPU は、x86 と ARM（AWS Graviton）から選べる。

## 選択肢

| 選択肢 | 良いところ | 悪いところ |
| --- | --- | --- |
| ECS（Fargate） | サーバーを管理せずにコンテナを動かせる。ALB・ブルー/グリーン・単発のタスク（マイグレーション）がそろっている。SA の面接で一番よく聞かれる構成 | 設定の項目が多い。動かしている間は、ずっと費用がかかる |
| App Runner | 設定が少なく、すぐに動かせる | ワーカーのように、リクエストを待たずに動き続ける処理に向かない。VPC やネットワークを細かく決められない |
| Lambda | 使った分だけの費用で済む | 1回の実行は最長15分。SQS を待ち続ける Celery のワーカーの形に合わない。最初の呼び出しが遅くなることがある |
| EC2 | 自由度が一番高い | OS の更新・監視・スケールを、すべて自分で管理する必要がある |

## 決めたこと

API とワーカーは **ECS の Fargate** で動かす。CPU は **ARM（Graviton）** にする。v0.1 のタスクの数は、API 1・ワーカー 1。

## 理由

- 同じ CPU とメモリなら、ARM のほうが x86 より安い。S0-11 の見積もりで、構成を ARM にした（Fargate の料金を下げた）
- API とワーカーで、同じ仕組み（タスク定義・サービス・ログ）を使えるので、覚えることが1つで済む
- 140 Day のカリキュラム（Day 132・133）と、AWS の SA の学習の両方に合う

## 捨てた選択肢

- **App Runner**：ワーカーの形に合わないので採らない
- **Lambda**：Celery のワーカーの形に合わないので採らない。ジョブを1件ずつ Lambda で動かす形に変えると、手順書の Celery の学習ができなくなる
- **EC2**：サーバーの管理に時間を取られるので採らない
- **x86**：費用が高いので採らない

## リスクと、その対策

- コンテナのイメージを **ARM 用（`linux/arm64`）** に作る必要がある。GitHub Actions では、ARM のランナーか、`docker buildx` で ARM 用にビルドする（S1-10）
- Python のライブラリ（画像の処理の Pillow など）が ARM に対応しているかを確かめる。対応していないものがあれば、そのときに x86 を検討する
