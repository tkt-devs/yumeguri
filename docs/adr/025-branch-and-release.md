# ADR-025: ブランチは main だけにし、本番には Release の公開で出す

- 状態：決定
- 日付：2026-10-30

## 背景

今後、2人以上で開発する可能性がある。そのときに、作りかけの機能が本番に出ないようにする方法と、ブランチの運用を決める。

## 選択肢

| 選択肢 | 良いところ | 悪いところ |
| --- | --- | --- |
| `main` だけ（GitHub Flow）＋ 本番は Release の公開で出す | ブランチが1つだけなので、どこに何があるかで迷わない。実務の案件でもよく使われる形なので、仕事と同じやり方を練習できる | `main` に入ったものは、すぐ staging に出る。staging を壊さないように、PR の段階で CI を通す必要がある |
| Git Flow（`main`・`develop`・`release/…`・`hotfix/…`） | 作りかけのもの（`develop`）と、本番に出ているもの（`main`）を、ブランチで分けられる | ブランチとマージの手順が多い。リリースのたびに、`main` と `develop` をそろえる作業が要る。staging・本番のデプロイのきっかけを、2つのブランチに分けて管理する必要がある |

## 決めたこと

- ずっと残すブランチは **`main` だけ**にする。作業は `feat/…`・`fix/…`・`docs/…` などの作業用のブランチで行い、PR で `main` に入れる
- マージは**マージコミット**にする。マージした作業用のブランチは、GitHub の設定で自動で消す
- **`main` へのマージで staging に出す**。コンテナのイメージには、コミット ID のタグを付ける
- **本番（production）には、GitHub の Release（`v0.1.0` のような版）を公開したときだけ出す**。staging で試したのと同じイメージを使い、作り直さない。`production` の Environment で、自分の承認を必須にする
- 急ぎの修正も、`fix/…` のブランチから `main` に入れ、新しい版（`v0.1.1` など）の Release で出す

## 理由

- 実務の案件でも、ずっと残るブランチは `main` だけにし、本番には Release の版で出す形がよく使われている。何人もで開発する案件でも、この形で回る
- 「作りかけのものを本番に出さない」は、ブランチを分けなくても、「Release を公開したものだけが本番に出る」というしくみで実現できる
- staging で試したイメージを、そのまま本番に出すので、「staging では動いたのに、本番では違うものが動いた」ということが起きない

## 捨てた選択肢

- **Git Flow**：手順が多く、staging と本番のデプロイのきっかけを2つのブランチで管理する必要がある。2人の規模では、その手間に見合う利点が小さいので採らない
- **Squash マージ**：PR の中のコミットが1つにまとまり、`main` の履歴が読みやすくなる一方で、まとめたコミットの名前が PR のタイトルになる。作業用のブランチのコミット（Conventional Commits の形）をそのまま残したいので採らない

## リスクと、その対策

- `main` が壊れると、staging も壊れる。`main` を保護し、PR と CI を必須にする（S1-03・S1-11）
- Release を公開したときに、`main` の先頭ではないコミットを指定すると、意図しない版が出る。Release は、出したいコミットに付けたタグから作る手順を Runbook に書く
