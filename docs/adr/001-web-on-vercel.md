# ADR-001: Web（Next.js）を Vercel で動かす

- 状態：決定
- 日付：2026-10-30

## 背景

画面は Next.js（App Router）で作る。銭湯の詳細のページは、表示を速くするために、作ったページを保存しておき、内容が変わったときだけ作り直す仕組み（ISR）を使う。Next.js をどこで動かすかを決める必要がある。

## 選択肢

| 選択肢 | 良いところ | 悪いところ |
| --- | --- | --- |
| Vercel | Next.js を作った会社のサービスなので、ISR・作り直し・PR ごとのプレビューが、設定なしで動く。無料のプラン（Hobby）がある | 無料のプランは、個人で非商用の利用だけに限られる。AWS の外に置くので、API（`api.`）とはドメインが分かれる |
| AWS Amplify Hosting | AWS の中で完結する | Next.js の新しい機能への対応が、Vercel より遅れることがある |
| ECS で Next.js のコンテナを動かす | API と同じ仕組みで管理できる | タスクが複数になると、ISR で保存したページを、タスクの間で共有する仕組み（共有のキャッシュ）を自分で作る必要がある |
| OpenNext ＋ Lambda | AWS の中で、サーバーなしで動かせる | 仕組みが複雑で、問題が起きたときに原因を追いにくい |

## 決めたこと

Web は **Vercel の無料のプラン（Hobby）** で動かす。`app.` のドメインを Vercel に向け、Cloudflare のプロキシは使わない（DNS だけにする）。

## 理由

- S0-11 の試作で、Vercel の上で ISR と、作り直しの入口（`revalidateTag`）が動くことを確かめた（`x-vercel-cache` が `HIT` → `REVALIDATED` → `HIT` になった）
- このアプリは学習用で、非商用なので、無料のプランの条件に合う
- 画面の配信のしくみを自分で作らずに済むので、時間を API と AWS の学習に使える

## 捨てた選択肢

- **Amplify Hosting**：Next.js の新しい機能（Cache Components など）への対応が遅れると、手順書のとおりに作れなくなるので採らない
- **ECS で Next.js を動かす**：共有のキャッシュを作る手間が、学習の目的（カリキュラムの Day）に比べて大きすぎるので採らない
- **OpenNext ＋ Lambda**：仕組みが複雑で、v0.1 の期間に収まらないので採らない

## リスクと、その対策

- 無料のプランは、上限（Functions の呼び出しが月100万回など）を超えると、その機能が止まる。止まっても請求はされない。上限に近づいたら、使い方を見直す
- 商用に使うことになったら、有料のプラン（Pro）に変える
- Web と API のドメインが分かれるので、Cookie と CORS の設計が必要になる（ADR-003）
