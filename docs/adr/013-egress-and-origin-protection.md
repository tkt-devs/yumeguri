# ADR-013: 外への出口は NAT の EC2 にし、ALB は Cloudflare からだけ届くようにする

- 状態：決定
- 日付：2026-10-30

## 背景

非公開のサブネットの ECS のタスクは、外（Google・Sentry・AWS の API）へ通信する必要がある。その出口を決める。あわせて、ALB に、Cloudflare を通らないリクエストが届かないようにする方法を決める。

## 選択肢

| 選択肢 | 良いところ | 悪いところ |
| --- | --- | --- |
| NAT ゲートウェイ | AWS が管理するので、手間がない | 1つで月 約46ドル（東京）。使っていなくても1時間ごとに費用がかかる |
| NAT の代わりの小さな EC2（`t4g.nano`） | 月 約4ドル | EC2 の設定と更新を自分で行う。1台なので、止まると外に出られない |
| タスクを公開のサブネットに置き、公開の IP を付ける | NAT が要らない | タスクに公開の IP が付き、外から狙われやすくなる。公開の IPv4 にも費用がかかる |

## 決めたこと

- 出口は **NAT の代わりの EC2（`t4g.nano`）を AZ-a に1台** 置く。送信元／送信先のチェックを無効にする。中に入るときは Session Manager を使い、SSH は使わない
- S3 への通信は、**ゲートウェイ型の VPC エンドポイント**（無料）を通し、NAT を通さない
- ALB は、**① セキュリティグループで Cloudflare の IP アドレスの範囲からの 443 だけを許し、② Cloudflare が付ける秘密のヘッダーがないリクエストを、リスナーのルールで 403 にする**

## 理由

- S0-11 の見積もりで、NAT ゲートウェイを EC2 に変えると、月 約42ドル安くなった
- タスクを非公開のサブネットに置いたまま、費用を下げられる
- Cloudflare の IP アドレスは、ほかの人の Cloudflare のアカウントからも使える。IP の範囲だけでは足りないので、秘密のヘッダーを組み合わせる

## 捨てた選択肢

- **NAT ゲートウェイ**：費用が高いので採らない（本格的に運用するときは、もう一度検討する）
- **タスクを公開のサブネットに置く**：タスクを外にさらすので採らない
- **Cloudflare の証明書で ALB との間を相互に認証する（mTLS）**：一番強いが、ALB の信頼ストアの設定が増えるので、v0.1 では採らない

## リスクと、その対策

- NAT の EC2 が止まると、タスクが外に出られない（Google のログインができなくなる）。CloudWatch のアラームで EC2 の状態を見張る
- EC2 の OS の更新を自分で行う必要がある
- Cloudflare の IP アドレスの一覧は変わることがある。Terraform の Cloudflare 用のプロバイダーから取得して、apply のたびに最新にする
- 秘密のヘッダーの値は Secrets Manager にも置き、定期的に変える
