# ADR-005: ワーカーを Python にし、DB のスキーマは Prisma だけが管理する

- 状態：決定
- 日付：2026-10-30

## 背景

写真の加工などの重い処理は、API から切り離して、ワーカーで非同期に動かす。ワーカーの言語と、ワーカーが DB をどう使うかを決める。

## 選択肢

| 選択肢 | 良いところ | 悪いところ |
| --- | --- | --- |
| Python（FastAPI・Celery） | 画像の処理などのライブラリが豊富。カリキュラムの Python・FastAPI・pytest の Day（101・112〜118）を学べる | TypeScript と Python の2つの言語を扱うことになる。Zod のスキーマを Python で使い回せない |
| TypeScript | API と言語・型をそろえられる | カリキュラムの Python の Day を学べない |

## 決めたこと

- ワーカーは **Python**（`services/worker`。FastAPI・Celery・uv）にする
- **DB のスキーマとマイグレーションは、Prisma（`prisma/`）だけが管理する**。ワーカーは表を作ったり変えたりしない
- ワーカーが読み書きする表は、**`Job` と `Photo` だけ**にする（v0.1）。ワーカー用の DB のユーザー（`yumeguri_worker`）を作り、この2つの表にだけ権限を与える（S1-04 の「DB のユーザーを3つに分ける」の3つ目）

## 理由

- カリキュラムの Python の Day を、このアプリの中で学べる
- スキーマを管理する場所を1つにすると、2つの言語でスキーマが食い違う問題が起きない
- ワーカーの DB のユーザーの権限を絞ると、ワーカーに不具合があっても、ほかの表を壊さない

## 捨てた選択肢

- **ワーカーも TypeScript にする**：カリキュラムの Python の Day を学べなくなるので採らない

## リスクと、その対策

- ジョブの中身（`payload`）の形を、TypeScript と Python で二重に定義することになる。ジョブの種類ごとに、Python 側でも検証（Pydantic）し、テストで形のずれを見つける
- Prisma のマイグレーションで表の名前や列を変えると、ワーカーの SQL が壊れる。`Job`・`Photo` を変えるマイグレーションでは、ワーカーのテストも必ず動かす
