# ADR-026: staging の CD は、CI の成功のあとに OIDC で入り、動いているときだけ入れ替える

- 状態：決定
- 日付：2026-11-11

## 背景

`main` にマージしたら、staging に自動で出したい（ADR-025）。そのときに、次の4つを決める。

- GitHub Actions から、どうやって AWS に入るか
- いつ動かすか（テストが落ちたコードを出さないために）
- staging は使うときだけ作る（ADR-022）。**止まっているときに、どうするか**
- 動かすイメージのタグを、どこに置くか（Terraform と CD のどちらが決めるか）

## 選択肢

**AWS への入り方**

| 選択肢 | 良いところ | 悪いところ |
| --- | --- | --- |
| OIDC（GitHub の身分証で、ロールを引き受ける） | 長く使える鍵を、どこにも置かない。鍵は1時間で使えなくなる。ロールを引き受けてよいリポジトリ・ブランチを、AWS 側で絞れる | 初めの設定（プロバイダー・信頼ポリシー）が要る |
| IAM ユーザーのアクセスキーを GitHub のシークレットに置く | 設定が簡単 | 漏れたら、取り消すまで使われ続ける。手順書の完了の条件（アクセスキーを置かない）に合わない |

**いつ動かすか**

| 選択肢 | 良いところ | 悪いところ |
| --- | --- | --- |
| CI が `main` で成功したら（`workflow_run`） | CI が落ちたコードは出ない | CI の分だけ、出るのが遅くなる |
| `main` への push で、CI と同時に | 速い | CI が落ちても出てしまう |

**イメージのタグの置き場所**

| 選択肢 | 良いところ | 悪いところ |
| --- | --- | --- |
| SSM のパラメータ（CD が書き、Terraform が読む） | up したときも、いちばん新しくデプロイしたイメージで作られる。tfvars を書きかえる手間がない | Terraform の外で値が変わる |
| tfvars に書き、CD が Terraform を apply する | タグがコードに残る | CD に、Terraform の全部を作れる強い権限と、Cloudflare のトークンが要る |

## 決めたこと

- **OIDC** で入る。デプロイ用のロールは、**このリポジトリの `main` の身分証（sub）からだけ**引き受けられる。sub は、リポジトリの名前を変えても変わらない形（owner と repo の ID 入り）
- CD は **CI が `main` で成功したあと**に動く（`workflow_run`）。手で動かすこともできる（`workflow_dispatch`）
- イメージは3つ（API・ワーカー・DB の準備用）。タグは Git のコミット ID の先頭 12 文字
- **staging が止まっていれば、イメージを押し上げてタグを記録するだけ**にする。動いていれば、DB のユーザーの作成 → マイグレーション → API・ワーカーの入れ替え → 新しい版で動いているかの確認 → タグの記録、の順に行う
- タグは **SSM のパラメータ**（`/yumeguri/staging/image-tag`）に置く。デプロイに成功したときか、止まっているときだけ書く
- デプロイ用のロールの権限は、ECR への押し上げ・タスク定義の登録・決められたサービスの入れ替え・決められた単発のタスクの実行・決められたロールを ECS に渡すこと、に絞る。Terraform は CD からは動かさない

## 理由

- 長く使える鍵を置かないのは、今の標準のやり方で、手順書の完了の条件でもある
- staging は、ふだん止まっている（ADR-022）。止まっているたびに CD が失敗すると、本当の失敗に気づけなくなる
- CD から Terraform を動かすと、CD のロールに VPC・RDS まで作れる権限が要る。権限を小さくするため、CD はタスク定義とサービスの入れ替えだけを行う

## 捨てた選択肢

- **アクセスキー**：漏れたときの被害が大きいので採らない
- **CI と同時に動かす**：落ちたコードが出るので採らない
- **CD から Terraform を apply する**：権限が大きくなりすぎるので採らない

## リスクと、その対策

- CD がタスク定義の新しい版を登録するので、Terraform の state の版とずれる。次に Terraform を apply すると、Terraform の版（同じタグの、同じ中身）に戻る。タグは SSM から読むので、イメージは変わらない
- マイグレーションは、新しいコードが動く前に流れる。古いコードが新しい表で動く時間があるので、マイグレーションは「前の版のコードでも動く形」で書く（列を消すときは、2回に分ける）
- 本番（production）の CD は、Release の公開で動かす（ADR-025）。S4 で、別のロール・別の Environment（承認つき）で作る
