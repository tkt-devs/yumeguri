# ADR-012: ジョブのキューは SQS、キャッシュ・nonce は ElastiCache（Valkey）にする

- 状態：決定
- 日付：2026-10-30

## 背景

非同期のジョブのキューと、短い時間だけ覚えておく値（QR の nonce・回数の上限・キャッシュ）の置き場所を決める。ElastiCache は、種類（Valkey か Redis か、ノード型かサーバーレス型か）も決める。

## 選択肢

| 選択肢 | 良いところ | 悪いところ |
| --- | --- | --- |
| キューは SQS、短い値は ElastiCache | SQS は、メッセージを失いにくく、失敗したメッセージの置き場所（DLQ）がある。それぞれの得意なことに使える | サービスが2つになる |
| キューも ElastiCache（Redis をブローカーにする） | サービスが1つで済む | ElastiCache が再起動したり、メモリが足りなくなったりすると、ジョブが消えることがある。DLQ がない |
| Amazon MQ | 本格的なメッセージのしくみ | 費用が高い。このアプリには機能が多すぎる |

## 決めたこと

- キューは **SQS**。`jobs-default`・`jobs-heavy` と、それぞれの DLQ を作る（Celery にキューを自動で作らせない）
- 短い値は **ElastiCache の Valkey 9.1**（ノード型・`cache.t4g.micro` を1台・クラスターモードなし・通信の暗号化（TLS）あり）

## 理由

- ジョブは失いたくないので、SQS に任せる
- Valkey は、Redis より安い（ノード型で 20%）。基本のコマンド（`SET`・`GET`・`NX`・`EX`）は Redis と同じ
- ノード型にしたのは、使うときだけ動かすなら、サーバーレス型との差が月 約0.5ドルしかないから。サーバーレス型は、TLS とクラスターモード対応のクライアントが必須で、ローカルの Docker（1台の Valkey）とつなぎ方が変わる

## 捨てた選択肢

- **キューも ElastiCache**：ジョブが消えることがあり、DLQ もないので採らない
- **Amazon MQ**：費用と機能が、このアプリに合わないので採らない
- **ElastiCache のサーバーレス型**：ローカルとつなぎ方が変わるので採らない

## リスクと、その対策

- 要件定義書の「Redis をブローカーにした比較の実験」は、S1-09 で行い、結果をこの ADR に追記する
- Valkey が再起動すると、nonce のメモが消える。QR の期限（60秒）が短いので、消えても使い回しの危険は小さい
