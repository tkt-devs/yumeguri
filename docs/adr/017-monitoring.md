# ADR-017: 監視は、v0.1 は CloudWatch と Sentry にし、X-Ray は v0.2 で足す

- 状態：決定
- 日付：2026-10-30

## 背景

障害に気づき、原因を調べるための監視のしくみを決める。要件定義書では、CloudWatch・X-Ray（トレース）・Sentry を使う。

## 選択肢

| 選択肢 | 良いところ | 悪いところ |
| --- | --- | --- |
| CloudWatch ＋ Sentry（v0.1）→ X-Ray を足す（v0.2） | v0.1 で最低限の監視がそろう。トレースは、ジョブやサービスが増えてから足せる | v0.1 では、1つのリクエストが、どのサービスでどれだけ時間を使ったかを追いにくい |
| 最初から CloudWatch ＋ X-Ray ＋ Sentry | 最初から全部が見える | v0.1 の期間に、設定の作業が増える |
| CloudWatch だけ | サービスが1つで済む | エラーの内容（スタックトレース）や、どの利用者で起きたかを追いにくい |

## 決めたこと

- v0.1 は **CloudWatch（Logs・メトリクス・アラーム）と Sentry** にする。ログは JSON で、相関 ID を必ず入れる
- **X-Ray（OpenTelemetry）は v0.2** で足す

## 理由

- v0.1 は、全部の分野を1つずつ通すことが目的なので、監視も最小の形にする
- 相関 ID がログにあれば、v0.1 の規模なら、CloudWatch Logs で1つのリクエストを追える
- Sentry は無料のプランで使え、エラーの内容を見やすくまとめてくれる

## 捨てた選択肢

- **最初から X-Ray**：v0.1 の期間に収まらないので、v0.2 に回す
- **CloudWatch だけ**：エラーの調査がしにくいので採らない

## リスクと、その対策

- Sentry にも、個人情報やシークレットを送らない設定にする（送る前に消す）
- アラームの通知の先（SNS → メール）を必ず作り、届くことを確かめる
